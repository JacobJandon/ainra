# The agent-identity landscape, counted

The site's landscape page states a number. This is the list behind it, so the number can be checked rather than
believed.

**Method, stated plainly.** Enumerated in **August 2026** from each party's own published material — its site, docs,
repository, specification, or its entry in a funder's public directory. Every row carries the link it was read from.
Where a claim could not be traced to a primary source it was dropped rather than softened; where a first pass
overstated a capability, an adversarial second pass corrected it and the correction stands. The file was re-checked
for changes on **12 November 2026**: a sweep for items dated 28 October to 12 November, with closer checks of the
Agent Name Service and the Personal Agent Protocol. The August rows were not each re-read. The counts table stays the
August floor, the file's convention; items found later, and corrections to the August rows, are listed in the dated
sections below the tables.

**This is a self-made enumeration, not a census.** No authoritative census exists — in February 2026 NIST's own
concept paper asked the public which standards were being used for AI-agent identity, because it could not
enumerate the field either. Treat every count here as a **floor**, not a total.

**What it is not.** This is not a comparison, a ranking, or a scorecard, and nothing here says these projects are
bad. Most solve a real problem, well. The point is narrower and structural: nearly all of them issue identity to
agents their own customer already controls, and none is a non-profit *operating* cross-vendor verification and
revocation. That is an observation about the shape of the field, not a judgement on anyone in it.

The last row is the one that matters, and it is the reason this file exists. Every non-profit below publishes a
specification or code, convenes a working group, or hosts a project. None of them runs the thing it describes. One
change since August: the Agent Name Service (ANS) launched as a Linux Foundation project on 10 November 2026. The
project publishes specifications and code and runs no registry, log or status service. The production ANS registry,
log and status service that its software points to are run by GoDaddy, a commercial company, so the count stays at
zero (see [Changes since 28 October](#changes-since-28-october-checked-12-november-2026)). The agent verification that
operates at scale at the network edge today is run by commercial vendors who also sell the product that blocks the
traffic.

## Revocation and attribution, specifically (checked 26 October 2026)

The question AINRA Link answers: *this key, from any issuer, belongs to an accountable operator, and is or is not
revoked, checked by anyone, offline.* Each entry below was read on its own published material. None answers that
question across providers today.

- **IETF OAuth Token Status List** is in the RFC Editor queue (draft-21, 21 June 2026): a signed, compressed bitstring
  the token itself must point to. The spec "does not mandate specific methods for key resolution and trust
  management". Keys that carry no status claim, such as signature-agent keys and OAuth clients, are outside it.
  <https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/>
- **W3C Bitstring Status List** became a Recommendation on 15 May 2025. It sets a minimum of 131,072 entries for herd
  privacy. <https://www.w3.org/TR/vc-bitstring-status-list/>
- **OpenID Shared Signals, CAEP and RISC** were approved as Final in September 2025. They push events between parties
  that have configured a stream in advance; strangers get no status.
  <https://openid.net/top-firms-test-interoperability-of-final-ssf-and-caep/>
- **The Web Bot Auth directory draft** covers rotation and expiry ("remove expired keys from the directory"), not
  revocation. The registry draft warns: "Malicious actors may put properties which are not theirs in the registry."
  <https://www.ietf.org/archive/id/draft-meunier-webbotauth-registry-03.txt>
- **Visa Trusted Agent Protocol** (14 October 2025) keeps an agent registry of public keys inside the network. Its
  repository documents no key revocation. <https://github.com/visa/trusted-agent-protocol>
- **The Ant International, Visa and Mastercard "Know Your Agent" framework** (10 September 2026) names "operator
  traceability across networks" first, while "each network will continue to use its own verification and decisioning
  processes". <https://thenextweb.com/news/visa-mastercard-ant-international-know-your-agent-ai-agents>
- **Microsoft Entra Agent ID** disables an agent identity so it stops "receiving tokens", inside Entra.
  <https://learn.microsoft.com/entra/agent-id/disable-agent-identities>
- **AWS AgentCore** signs Web Bot Auth requests for its customers: AWS "handles credential generation, request signing,
  and identity registration", so attribution stops at the platform.
  <https://aws.amazon.com/about-aws/whats-new/2025/10/amazon-bedrock-agentcore-browser-web-bot-auth-preview>
- **DigiCert AI Trust Manager** (15 September 2026) describes an "AI Passport" connected "to an accountable owner",
  with a kill switch at the source. It names no mechanism, and it is a commercial certificate authority.
  <https://www.digicert.com/news/every-ai-agent-needs-a-kill-switch-digicert-launches-ai-trust-manager>
- **DNSid** (draft-ihsanullah-dnsid-01, 29 June 2026) is the closest design: a status endpoint that "MUST NOT report
  ... verified-ACTIVE when current status is unavailable or stale", sitting "beneath" other identity systems. It needs
  an online check and is run by one domain-registry company. <https://www.ietf.org/archive/id/draft-ihsanullah-dnsid-01.html>
- **ANS** (agent name service) revokes through CRL/OCSP with a 300 s TTL; its reference implementation "uses mock
  cryptography" according to an independent review.
  <https://labs.cloudsecurityalliance.org/research/agentic-identity-ans-security-analysis-v1-0/>
  **Corrected 12 November 2026:** that review covers the earlier OWASP-lineage design and one individual's reference
  code, not the Linux Foundation ANS, which publishes no CRL or OCSP and revokes through its log, with status tokens
  that last one hour by default (see [Changes since 28 October](#changes-since-28-october-checked-12-november-2026)).
- **The web PKI's own lesson.** Let's Encrypt switched its OCSP responders off on 6 August 2025, for privacy and
  reliability (<https://letsencrypt.org/2024/12/05/ending-ocsp/>). Firefox now downloads every revocation, about
  300 kB a day, because "the only secure approach is to check all revocations"
  (<https://hacks.mozilla.org/2025/08/crlite-fast-private-and-comprehensive-certificate-revocation-checking-in-firefox/>).

## Agents that must trust strangers (checked 28 October 2026)

- **Centre for Cryptographic Trust Infrastructure (CCTI), Cambridge.** Announced 7 October 2026 by Martin Kleppmann,
  with a £2.4m grant from ARIA's Scaling Trust programme; partners: the Cambridge Computer Laboratory, the SINE
  Foundation, Ink & Switch and Light Squares. Its question: "How is your agent supposed to know if the other agents are
  telling the truth?" Its approach: zero-knowledge proofs that a *claim* is true (emissions, provenance), built from
  evidence such as TLSNotary-authenticated bank records, DKIM-signed email and signed sensor data. It does not
  address identity, revocation or transparency logs by name. **Relation to AINRA:** complementary layers. CCTI proves
  what an agent says; AINRA says which accountable operator stands behind the key that said it, and whether that is
  still true. A proof from a revoked or unattributable key is worth little.
  <https://martin.kleppmann.com/2026/10/07/centre-for-cryptographic-trust-infrastructure.html>
- **ARIA Scaling Trust.** "Nearly £50m" for secure coordination of AI agents in three tracks (Arena competitions,
  open-source tooling, fundamental research). The page says rolling funding is "currently open" for Tracks 2 and 3;
  eligibility is not stated on that page. A candidate funding route for open-source revocation and attribution
  tooling (Track 2). <https://aria.org.uk/opportunity-spaces/trust-everything-everywhere/scaling-trust>
- **Fetch.ai.** An architecture paper (Wooldridge et al., arXiv 2510.18699, v2 September 2026) describes on-chain
  services for agent identity, discovery and transactions, with a logistics demonstration of agents that discover,
  negotiate and transact. It names no revocation or reputation mechanism; one freight company reports a pilot. No
  independent evidence of large-scale production use was found. **Relation:** a network whose agent keys could be
  linked to accountable operators across networks. AINRA Link takes Ed25519 and, since D-082, ES256K (secp256k1)
  keys — the key type such networks sign with. <https://arxiv.org/abs/2510.18699>
- **Attestix.** Open documentation tooling that produces Ed25519-signed, machine-readable EU AI Act evidence for
  agents (data governance, lineage, conformity records, verifiable presentations checkable "without contacting
  Attestix"). It says plainly it is not a conformity determination. No revocation or audit-log mechanism is
  described. **Relation:** close to AINRA's decision records in purpose, different in subject: evidence about how a
  system was built, against evidence of what a gate decided. Neither replaces the other.
  <https://attestix.io/docs/guides/eu-ai-act-compliance>
- **IRONVALD, "The passport problem" (29 September 2026).** About government passports, not agents: long-lived
  identity documents signed today will still be in use after a cryptographically relevant quantum computer exists,
  so their signatures are the exposure. **Relation:** an outside statement of the reason AINRA signs every passport
  with Ed25519 *and* ML-DSA-65 and refuses either alone. IRONVALD itself sells critical-infrastructure defence and
  does not work on agent identity. <https://ironvald.com/news/the-passport-problem>

  DNS publication, transparency, integrity monitoring and agent-to-agent authentication. The release says the
  specification "is now formalized"; the project's site says "The published specifications are drafts under active

- **How ANS revokes, and which agents it covers.** A registration is revoked by the agent's hosting platform or by the
  RA that holds it (ANS-1). The RA's private CA "publishes no CRL or OCSP endpoint"; instead "The TL is the revocation
  channel": the badge shows REVOKED and the status-token endpoint returns 410 (ANS-6). A status token is signed by the
  log's key and lasts one hour by default, an operator setting (ANS-4), and a verifier "MUST treat the inability to
  obtain a fresh status token as equivalent to revocation, subject to the failure policy in §9" (ANS-6). With the
  log's keys cached, a verifier checks receipts and status tokens offline; the one recurring network call is each
  agent refreshing its own token, so an offline check stays current to within one token lifetime plus clock skew
  (ANS-6 §9.2), and longer if a deployment uses the grace window of ANS-6 §9.4, which accepts a recently expired
  token. Every registration needs a domain name ("Every agent registration MUST have an FQDN primary anchor", a rule
  ANS-0 calls a policy, "not a structural limit"), at least one endpoint on that host, and a server certificate
  ("Server Certificates are required."). Open on 12 November 2026: proposals for
  personal agents without a domain or inbound endpoint (ans-spec #75), for a hosted provider registering agents for
  operators with no domain and no key (ans-spec #76), for making the server certificate optional (ans-spec #80), and
  for admitting agent sessions that hold no ANS certificate (ans-gateway-auth #20). Closed as not planned on
  11 September 2026: verifying agents not registered in ANS (ans #99 and ans-sdk-go #65; "ans-verify will remain an
  ANS verifier") and Web Bot Auth as an identity kind (ans #102).

## Naming collisions worth knowing about

There is no naming authority for any of this, and it shows. "Agent Passport" is claimed by several unrelated
parties at once; "Know Your Agent" is in use by numerous unrelated parties. "Agent Name Service" is not a collision,
as this file once said: the 2025 OWASP paper and the 2026 Linux Foundation project are one lineage, the second
building on the first (corrected 12 November 2026). Names in this file refer to the linked artifact and nothing else.
