Claim & Reach.

Agents that already exist don't start over — they get claimed. And once verified, they become safely reachable. Both specified in Standard v5.1; both ship with the first registrars.

CLAIM — PROVE CONTROL, KEEP HISTORY

Bind an existing agent to an accountable identity by proving control of it. Provenance is preserved and the old identifier becomes an alias — never the identity. Wanting it is not owning it: no proof, no claim, and a contested claim freezes rather than transfers.

→
REACH — VERIFIED, REACHABLE, NEVER SURVEILLED

Opt-in signed endpoints let anyone resolve where to reach an agent and know the endpoint provably belongs to it. Inboxes can require a valid passport from callers — both sides verified in milliseconds. The root never carries a message: the lookup is ours, the conversation is yours.

By key SIGNATURE

The agent signs a claim challenge with the key it already uses. Control of the key is control of the claim.

By wallet ON-CHAIN

An on-chain agent proves its registry entry by signing from the controlling wallet. The chain identifier becomes an alias with provenance.

By domain WELL-KNOWN

A domain-anchored agent publishes the challenge at a well-known path. The domain becomes reach metadata — the identity persists even if the domain doesn't.

The passport, field by field

Every line has a job.

Each numbered key below names one field on the agent passport, in order — the same specimen shown on the home page.

1
LINEAGE

The agent's permanent identity — soulbound, held for life, the thing history attaches to. Is this the same agent I dealt with before?

2
VERSION

Re-certified on every material change — model, permissions, operator — so trust always describes what's running today. What exactly is running right now?

3
OPERATOR

The verified legal entity responsible for the agent — where accountability lives if something goes wrong. Who do I hold responsible?

4
REGISTRAR

The independent, accredited issuer that did the verification and signed the passport. Its certificate chains to the root. Who vouched, under what rules?

5
AUTHORITY CLASS

Who stands behind it: a human (proven in zero-knowledge), an organization, another agent along a provable chain — or, declared honestly, fully autonomous. On whose behalf is this acting?

6
ASSURANCE TIER

How much verification stands behind the passport, L0 to L4. The root labels; every verifier chooses its own floor. How much can this credential carry?

7
ISSUING AUTHORITY + MRZ

The machine-readable zone any system can parse in one pass — with the canonical name, validity dates, and key fingerprint printed above it. Mandates and running fleets live outside the document, at the edge, where they belong. Can my software read this without custom integration?

8
ROOT ATTESTATION

The live status: chain valid, witnesses agree, entry sealed in the public log, in good standing — re-checked at every verification. Is this still good, right now?
